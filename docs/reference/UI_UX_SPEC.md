# Business OS — Спецификация пользовательского интерфейса и опыта

**Версия:** 1.0  
**Статус:** базовая спецификация  
**Назначение:** определить структуру интерфейса Business OS, ключевые пользовательские сценарии, правила навигации, отображения качества данных, работы с документами, Reality Alignment, AI-анализом и управленческими решениями.

---

## 1. Цель

UI/UX Business OS должен помогать пользователю понимать:

- что известно системе;
- насколько этим данным можно доверять;
- какие документы актуальны;
- где есть расхождения с реальной деятельностью;
- какие выводы подтверждены;
- каких данных не хватает;
- что рекомендует система;
- какое решение принял человек;
- каков фактический результат решения.

Интерфейс не должен создавать ощущение ложной уверенности.

Главная задача UX:

> Сделать сложную аналитическую систему понятной, доказательной и управляемой.

---

## 2. Основные принципы UX

### 2.1. Evidence Before Action

Пользователь сначала видит доказательства, затем действие.

### 2.2. Trust Is Visible

Trust Index, свежесть, полнота и конфликты не прячутся в настройках.

### 2.3. Facts Are Separate

Факты, наблюдения, гипотезы, рекомендации и решения визуально разделяются.

### 2.4. Progressive Disclosure

На первом уровне показывается краткий вывод.

На следующих уровнях:

- расчет;
- факты;
- связи;
- источник;
- оригинал документа;
- история.

### 2.5. No Dead Ends

Любое проблемное состояние должно предлагать следующий шаг:

- загрузить данные;
- назначить владельца;
- подтвердить факт;
- разрешить конфликт;
- открыть источник;
- обновить документ.

### 2.6. Human Approval Is Explicit

Подтверждение критического действия всегда должно быть отдельным осознанным шагом.

### 2.7. Consistency

Одинаковые сущности должны иметь одинаковые паттерны:

- карточка;
- статус;
- история;
- владелец;
- источник;
- Trust;
- связи;
- действия.

## 3. Целевые пользователи

### 3.1. Руководитель компании

Основные задачи:

- увидеть состояние компании;
- оценить готовность данных;
- задать вопрос;
- получить рекомендации;
- принять решение;
- проконтролировать результат.

### 3.2. Руководитель подразделения

Основные задачи:

- видеть KPI и процессы отдела;
- подтверждать расхождения;
- исправлять документацию;
- отвечать на запросы данных;
- контролировать решения.

### 3.3. Владелец процесса

Основные задачи:

- поддерживать описание процесса;
- сравнивать нормативную и фактическую модели;
- подтверждать изменения;
- отслеживать отклонения.

### 3.4. Владелец документа

Основные задачи:

- управлять версиями;
- подтверждать актуальность;
- разрешать конфликты;
- утверждать новую редакцию.

### 3.5. Владелец данных

Основные задачи:

- контролировать источник;
- исправлять ошибки;
- подтверждать mapping;
- разрешать дубли;
- следить за свежестью.

### 3.6. Аналитик

Основные задачи:

- исследовать знания;
- создавать запросы;
- проверять расчеты;
- анализировать связи;
- готовить материалы руководителю.

### 3.7. Сотрудник

Основные задачи:

- видеть свою должность;
- обязанности;
- KPI;
- процессы;
- назначенные задачи;
- доступные документы;
- запросы подтверждения.

### 3.8. Аудитор

Основные задачи:

- просматривать историю;
- проверять источники;
- анализировать изменения;
- проверять решения и права.

### 3.9. Администратор

Основные задачи:

- пользователи;
- роли;
- источники;
- коннекторы;
- системные настройки;
- мониторинг;
- безопасность.

## 6. Глобальный индикатор готовности данных

В верхней панели должен отображаться компактный индикатор:

```text
Completeness: 78%
Trust: 84
Alignment: 71
Critical Conflicts: 3
```

При нажатии открывается подробная панель.

---

## 7. Цвет и смысл

Цвет не должен быть единственным способом передачи статуса.

Минимальные статусы:

- зеленый + текст — подтверждено;
- желтый + текст — требует внимания;
- красный + текст — критическая проблема;
- серый + текст — нет данных;
- синий + текст — информационное;
- фиолетовый + текст — AI-предложение;
- штриховка или отдельная метка — симуляция.

- возможность закрыть экран;
- уведомление о завершении.

Не следует показывать фиктивный процент без реальных данных.

---

## 52. Partial Data State

Интерфейс должен явно показывать:

- доступную часть;
- отсутствующую часть;
- влияние;
- ограничения;
- возможные действия.

---

## 53. Stale Data State

Показываются:

- дата последнего обновления;
- допустимая свежесть;
- источник;
- затронутые показатели;
- действие синхронизации.

---

## 54. Conflict State

Показываются:

- конфликтующие значения;
- источники;
- приоритет;
- влияние;
- владелец;
- статус проверки.

---

## 55. Accessibility

Минимальные требования:

- WCAG-ориентированные контрасты;
- клавиатурная навигация;
- видимый focus;
- alt-тексты;
- aria labels;
- масштабирование текста;
- понятные ошибки;
- цвет не единственный сигнал.

---

## 56. Responsive Design

### Desktop

Полная функциональность.

### Tablet

Просмотр, подтверждение, анализ, решения.

### Mobile

- сводка;
- уведомления;
- просмотр анализа;
- принятие решения;
- комментарии;
- контроль результата.

---

## 57. Локализация

Система должна поддерживать:

- русский язык как основной;
- единый словарь терминов;
- локальные форматы даты;
- валюты;
- числа;
- часовые пояса;
- единицы измерения.

---

## 58. Экспорт

Экспорт должен сохранять:

- заголовок;
- дату;
- автора;
- источники;
- Trust;
- ограничения;
- статус конфиденциальности;
- версию.

---

## 59. Горячие клавиши

Минимально:

- глобальный поиск;
- новый вопрос;
- открыть уведомления;
- перейти назад;
- сохранить;
- закрыть панель.

---

## 60. Аналитика UX

Система может измерять:

- время до источника;
- время до решения;
- долю открытых доказательств;
- долю заблокированных анализов;
- время разрешения конфликта;
- ошибки пользователя;
- отказ от действий;
- использование фильтров;
- полезность рекомендаций.

---

## 61. UX-антипаттерны

Запрещено:

- скрывать низкий Trust;
- показывать AI-вывод как факт;
- использовать бесконечные модальные окна;
- перегружать Dashboard;
- автоматически подтверждать критические изменения;
- показывать граф без объяснения;
- заставлять пользователя искать источник вручную;
- смешивать старые и актуальные версии;
- скрывать ограничения анализа;
- использовать технические ошибки без перевода.

---

## 62. MVP UI

Первая версия должна включать:

1. вход;
2. главную страницу;
3. документы;
4. карточку документа;
5. извлеченные утверждения;
6. просмотр оригинала;
7. Reality Alignment;
8. карточку расхождения;
9. Knowledge Base;
10. карточку объекта;
11. KPI;
12. AI-анализ;
13. мнения агентов;
14. рекомендации;
15. решение;
16. Decision Memory;
17. Data Quality;
18. источники;
19. глобальный поиск;
20. аудит.

---

## 63. Критерии приемки MVP

MVP считается готовым, если пользователь может:

- загрузить документ;
- подтвердить утверждение;
- открыть источник;
- увидеть фактическое расхождение;
- подтвердить или отклонить его;
- найти объект;
- открыть связи;
- увидеть Trust;
- задать вопрос;
- увидеть блокировку;
- просмотреть мнения агентов;
- открыть доказательства;
- принять решение;
- поставить контроль;
- проверить результат.
