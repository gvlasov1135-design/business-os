---

# 1. Название проекта

**Business OS** — интеллектуальная операционная система одной компании.

Проект создается сначала для одной конкретной организации, чтобы система могла глубоко изучить ее структуру, процессы, документы, KPI, сотрудников, финансовые потоки, историю решений и внутренние правила.

Business OS не является обычной CRM, ERP, BI-системой или корпоративным порталом. Это единое цифровое пространство компании с цифровым двойником, непрерывной цифровой нитью данных и независимым советом AI-агентов.

---

# 2. Цель проекта

Создать платформу, которая:

- объединяет все данные компании в единой модели;
- поддерживает данные в актуальном состоянии без постоянного ручного импорта;
- создает цифровой двойник компании;
- предоставляет каждому сотруднику личное рабочее пространство;
- связывает сотрудников, документы, задачи, процессы, KPI, клиентов, платежи и решения;
- проверяет полноту, качество и достоверность данных;
- не допускает фантазирования AI при отсутствии информации;
- использует сеть независимых специализированных AI-агентов;
- объясняет каждую рекомендацию и показывает доказательства;
- оставляет окончательное решение за человеком;
- запоминает принятые решения и сравнивает прогнозы с результатами.

# 3. Главные принципы

## 3.1 Truth First

AI не имеет права придумывать факты, значения, причины, документы или события.

Если критических данных недостаточно:

1. Анализ останавливается.
2. Агент перечисляет отсутствующие данные.
3. Агент объясняет, почему без них нельзя продолжать.
4. Агент предлагает способ получения данных.
5. При необходимости создается запрос ответственному сотруднику.

Главное правило:

> Если данных недостаточно, система задает вопросы, а не придумывает ответы.

## 3.2 Explain Everything

Любой вывод должен иметь:

- источник;
- дату и время данных;
- использованные записи;
- формулу или метод расчета;
- сработавшие правила;
- ограничения;
- уровень достоверности;
- альтернативные варианты;
- причины отклонения альтернатив.

## 3.3 Human in Control

AI может:

- анализировать;
- искать проблемы;
- строить прогнозы;
- моделировать сценарии;
- рекомендовать действия;
- создавать черновики задач;
- готовить документы;
- предлагать автоматизации.

Без подтверждения человека AI не может:

- отправлять деньги;
- увольнять сотрудников;
- подписывать договоры;
- менять стратегию;
- удалять критические данные;
- выполнять необратимые действия;
- принимать финальные управленческие решения.

## 3.4 Independent Analysis

Каждый специализированный AI-агент сначала анализирует вопрос независимо и не видит выводы остальных агентов.

Только после завершения независимого анализа запускается этап обсуждения и объединения результатов.

## 3.5 Data Trust First

До запуска бизнес-анализа система должна определить, можно ли доверять данным.

# 4. Концепция продукта

Business OS состоит из пяти основных слоев:

1. **Core Platform** — пользователи, роли, объекты, документы, права, история.
2. **Digital Twin** — цифровая модель компании и связи между сущностями.
3. **Living Digital Thread** — непрерывный поток событий и изменений.
4. **Data Trust Layer** — проверка полноты, качества и достоверности.
5. **AI Intelligence Layer** — независимые агенты, прогнозы и рекомендации.

## 6.2 Требования

- уникальный ID;

# 12. Trust Index

Заполненность и достоверность — разные показатели.

Trust Index должен учитывать:

- полноту;
- свежесть;
- согласованность;
- надежность источника;
- подтверждение из других источников;
- качество заполнения;
- количество конфликтов;
- наличие аномалий;
- происхождение данных.

Пример базовой формулы:

```text
TrustIndex =
  completeness * 0.25 +
  freshness * 0.15 +
  consistency * 0.20 +
  sourceReliability * 0.15 +
  crossValidation * 0.15 +
  dataQuality * 0.10
```

Веса должны быть настраиваемыми.

## Режимы

- 90–100: высокая достоверность;
- 75–89: допустимо с предупреждениями;
- 60–74: ограниченный анализ;
- ниже 60: стратегические рекомендации запрещены.

Каждый KPI, вывод и прогноз должен иметь собственный Trust Score.

# 13. Data Doctor

Отдельный AI-модуль для диагностики и исправления данных.

Он должен находить:

- дубли;
- пропущенные обязательные поля;
- неправильные форматы;
- невозможные значения;
- резкие аномалии;
- конфликты источников;
- устаревшие данные;
- нарушения бизнес-правил;
- несвязанные записи;
- подозрительные ручные изменения.

## Поведение

Data Doctor не исправляет критические данные автоматически без подтверждения.

Он:

1. Обнаруживает проблему.
2. Объясняет ее.
3. Показывает затронутые объекты.
4. Предлагает исправление.
5. Показывает ожидаемое влияние на Trust Index.
6. Создает задачу ответственному сотруднику.
7. После подтверждения применяет исправление.

# 14. Протокол отсутствующих данных

Перед анализом агент должен сформировать `RequiredDataManifest`.

Пример:

```json
{
  "analysisType": "cash_flow_forecast",
  "required": [
    "bank_balances",
    "scheduled_payments",
    "accounts_receivable",
    "accounts_payable"
  ],
  "optional": [
    "sales_forecast",
    "seasonality_history"
  ]
}
```

Если отсутствует required-поле:

- статус анализа `blocked_missing_data`;
- создается Data Request;
- агент не формирует финальный вывод;
- пользователю показывается список требований.

Допустимы только явно обозначенные сценарные предположения, если пользователь сам их ввел и подтвердил.

## 15.2 Этапы работы совета

3. Каждый агент получает одинаковую постановку и свой разрешенный набор данных.
4. Каждый агент формирует независимое заключение.

6. После завершения запускается cross-review.
7. Challenger AI ищет слабые места и ошибки.
8. Executive AI формирует синтез.
9. Руководитель получает варианты решения.
10. Руководитель утверждает, отклоняет или отправляет на доработку.

# 29. Самый первый рабочий сценарий

10. Challenger AI проверяет выводы.
11. Executive AI формирует итог.
12. Руководитель принимает решение.
13. Решение сохраняется в Decision Memory.
14. Создаются задачи на выполнение.
15. Система отслеживает результат.

# 30. Definition of Done для AI-ответа

AI-ответ считается готовым, только если:

- указан статус анализа;
- проверены необходимые данные;
- нет неподтвержденных фактов;
- перечислены источники;
- указан Trust Score;
- показаны ограничения;
- отделены факты от интерпретаций;
- перечислены альтернативы;
- указаны риски;
- нет выполнения критического действия без подтверждения;
- ответ сохранен в журнале.

# 32. Требования к Cursor

При генерации кода Cursor должен:

- следовать доменной архитектуре;
- не создавать бизнес-логику внутри UI;
- использовать строгую типизацию;
- валидировать входные данные;
- создавать миграции;
- писать тесты для критической логики;
- использовать idempotent handlers для событий;
- сохранять audit trail;
- не внедрять автоматические критические действия;
- не смешивать подтвержденные факты и AI-выводы;
- хранить версии промптов и правил;
- оставлять расширяемые интерфейсы для коннекторов и агентов.

---

# 33. Что не делать в начале

- не делать сразу универсальный SaaS;
- не поддерживать десятки отраслей;
- не создавать двадцать агентов;
- не строить полноценную ERP;
- не использовать AI без источников;
- не разрешать AI изменять критические данные самостоятельно;
- не пытаться обучать собственную LLM с нуля;
- не усложнять микросервисами до появления нагрузки;
- не делать ручной ввод основным способом обновления данных.

# 34. Основное позиционирование

**Business OS — единая интеллектуальная среда одной компании, которая объединяет документы, людей, процессы, KPI и данные в цифровой двойник, поддерживает его актуальность через живую цифровую нить и помогает руководителю принимать объяснимые решения с помощью независимого совета AI-агентов.**
